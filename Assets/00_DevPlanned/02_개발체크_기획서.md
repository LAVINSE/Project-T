## 1. 문서 목적과 진행 규칙

**앞으로 모든 개발 작업은 해당 기능의 구성·세부 동작·표시 방식·화면 전환을 사용자에게 구체적으로 확인받고, 합의된 범위에서 구현한다.** 로드맵에 등록되어 있거나 기능의 큰 방향이 채택되었다는 이유만으로 세부 기획까지 임의로 결정하지 않는다. 사용자와 작업 내용을 단계적으로 조정하는 절차는 1.2절을 따른다.

이 문서는 개발할 기능, 선행 결정, 완료 조건, 검증 증거를 연결한다. **초원 스테이지 1의 구매·이동·교전·부활·3라운드·승패·재시작에 이어 0.9에서 공방 실제 공격과 라운드/최종 휴식을 실제 장면에 연결했다.** 0.8·0.8.1에서 확정한 규칙 중 장비 2슬롯, 특별 전리품 직접 확보와 실패 보존, 위협 강화, 공방 연금, 다중 스킬 교체는 구현 대기다. 영구 성장·선택 업그레이드·장비 제작/드롭·파밍 정산·저장·후속 스테이지도 구현 대기다. 0.7 실행 증거와 0.8·0.8.1 결정 당시 상태는 역사 기록으로 유지하며 공통 전투 화면 검증은 2.13절, 데이터 편집·보상 기반의 최신 범위는 2.14절을 따른다.

0.13에서는 사용자 요청으로 **찾기·만들기·수정하기·검사하기·확인하기를 지원하고, 사용자가 직접 데이터를 편하게 제작할 수 있는 편집기**를 정식 개발 작업에 포함한다. 전리품 구현 전에 공통 편집 기반을 준비하고, 각 기능과 전용 데이터 편집을 함께 개발하며, 콘텐츠 대량 제작 전에 비교·일괄 수정·전체 검사를 갖춘다. 0.13 당시에는 계획 등록이었으며, 0.16 현재 공통 편집기 7종과 보상 정의·수량·독립 확률 편집을 구현했다. 직접 제작 전 과정의 실전 확인과 아이템 보관·영구 저장, 표 비교·일괄 수정은 별도 후속 범위다.

| 상태 | 의미 |
| --- | --- |
| 작성 완료 | 문서 또는 근거가 작성됨 |
| 결정 대기 | 사용자 선택이 필요함 |

| 진행 | 구현 또는 검증 중 |

체크 표시는 검증이 끝난 경우에만 사용한다. 사용자 답변이 없는 설계는 추천안을 기록하되 확정으로 바꾸지 않는다. 대기 항목과 무관한 문서 정리·읽기 전용 조사는 계속할 수 있다.

- [ ] 구현 중 새로 생긴 결정과 변경 사항도 확인받아 합의 내용에 반영했다.

### 1.2 기능별 상세 확인과 작업 조정 — 2026-09-21 사용자 확정

이 규칙은 화면뿐 아니라 데이터 편집기·전투·재화·성장·저장·콘텐츠 제작 등 이후의 모든 개발 작업에 적용한다. 기능을 한꺼번에 추측하여 완성하지 않고, 사용자가 상세 내용을 결정하고 조정할 수 있도록 작업 단위를 나눈다.

1. **착수 전 조사:** 관련 기획서·기존 코드·사용자 제작 자산을 확인하고, 이미 확정된 내용과 새로 결정할 내용을 구분한다. 확인에 필요한 읽기 전용 조사와 구체안 작성은 먼저 진행한다.
2. **상세안 제시와 질문:** 아래 항목 중 해당 기능에 필요한 내용을 구체적으로 설명한다. 필요한 경우 화면 구성표·전환 흐름·선택지와 차이를 함께 제시하여 사용자가 구현될 결과를 판단할 수 있게 한다. 단순히 “이 기능을 만들까요?”만 묻고 세부 내용을 임의로 정하지 않는다.
3. **합의 기록 후 구현:** 사용자 답변을 기획서와 작업의 완료 조건에 반영하고, 확정된 부분부터 구현한다. 답변이 없는 제안은 확정으로 취급하지 않으며 그 결정에 의존하는 구현은 대기한다.
4. **작업 중 확인과 조정:** 새로운 항목·예외 처리·화면 동작·저장 정책이 필요하거나 합의한 설계를 바꿔야 하면 해당 부분의 구현을 멈추고 질문한다. 원인·선택지·영향을 설명하고 답변 후 반영한다. 확인 대기와 무관한 조사·검증 및 이미 합의된 범위는 진행할 수 있다.
5. **중간 결과와 최종 결과 공유:** 화면이나 기능을 확인할 수 있는 단계에서 실제 결과를 보여 주고 세부 조정을 받는다. 합의한 완료 조건으로 검증한 뒤 구현 범위·검증 결과·남은 결정을 기록한다. 다음 기능으로 넘어갈 때도 그 기능의 상세 확인 절차를 거친다.

이미 사용자가 명시한 사항은 반복해서 허락을 구하지 않고 적용할 내용으로 정리한다. 새로 필요한 결정에 집중하며, 내부 코드 정렬처럼 기능·표시·조작·저장 규칙을 바꾸지 않는 구현 세부까지 매번 확인 대상으로 늘리지는 않는다. 사용자가 특정 세부 사항을 명시적으로 위임한 경우에는 그 범위 안에서 결정하고 결과를 설명한다.

| 확인 항목 | 사용자와 정할 내용 |
| --- | --- |
| 목적과 범위 | 어떤 상황에서 쓰는 기능인지, 이번에 포함할 항목과 나중에 만들 항목 |
| 항목별 세부 규칙 | 가능한 값·단위·범위·기본값·조건·제한, 각 항목이 실제로 바꾸는 내용 |
| 표시 방식 | 표시할 정보·문구·아이콘·배치·버튼·슬라이더 등 조작 요소, 활성·비활성·빈 상태 표현 |
| 입력과 처리 시점 | 클릭·드래그·선택 등 입력, 즉시 적용 또는 적용 버튼, 취소·되돌리기·초기화의 의미 |
| 화면 전환 | 진입 위치, 같은 팝업의 내용 교체·하위 페이지·별도 팝업 여부, 뒤로 가기·닫기·다시 열기 동작 |
| 데이터와 저장 | 사용할 데이터, 변경 대상과 수명, 저장 시점, 장면 이동·재시작 후 유지 여부 |
| 예외와 검증 | 사용할 수 없는 조건과 안내, 오류·참조 누락 처리, 사용자가 확인할 대표 동작과 완료 조건 |

**설정 팝업을 작업할 때의 확인 예시 — 아직 설정 기능의 확정 사양이 아님:**

- 어떤 설정 항목을 넣을지 먼저 정한다. 소리·화면·조작 같은 분류도 제안으로 제시하고 확인받는다.
- 각 항목의 선택값·범위·기본값, 표시 문구와 조작 형태, 적용·취소·저장 방식을 확인한다.
- “상세 설정”을 누르면 같은 팝업이 세부 페이지로 바뀌는지, 별도 팝업을 여는지 확인한다. 뒤로 가면 어디로 돌아오는지와 변경값 유지 여부도 함께 정한다.
- 팝업 열기·닫기와 게임 정지의 관계, 초기화·다시 열기·게임 재실행 시 동작을 확인한다.

확인 기록에는 작업 번호·합의한 범위·사용자 답변·미정 항목·완료 조건을 남긴다. 이후 답변으로 바뀐 규칙은 최신 합의로 갱신하고 이전 결정은 변경 기록으로 구분한다.

### 1.3 데이터 편집과 보상 기반 합의 — 2026-09-21 최종 반영

- Unity CLI로 개발한다. `Project T > 데이터`에 클래스·적·스테이지·경로·외형·재화·아이템 독립 창 7종을 둔다. SWUtils 탭에는 추가하지 않는다.
- 목록과 오른쪽 입력 모두 SWUtilsDataEditor처럼 정리한다. 아이콘·자산명·타입의 한 줄 목록, 검색, 간결한 인스펙터를 사용하고 내부 데이터 분류 탭과 큰 기능 탭을 제거한다.
- 상단은 새로 만들기·복제, 선택 데이터는 되돌리기·적용·저장을 제공한다. 검사·미리보기·참조와 사용처·시험·실행 취소는 도구 메뉴에 모은다. 한글 설명은 입력 툴팁으로 제공한다.
- 원본을 유지한 초안을 편집하고 검사 후 한 번에 적용·저장한다. 외부 원본 변경을 감지하며 같은 Unity 세션의 재열기·재컴파일에서 종류별 초안을 복원한다.
- 유효한 템플릿으로 생성·복제하고 종류별 폴더에 저장한다. 첫 재화·아이템은 기본 양식으로 생성한다. 연결 자산은 공유하고 필요할 때 개별 복제한다. 시험은 원본 장면과 전투 데이터의 복사본으로 진행한다.
- 재화·아이템 자산의 기본 수량에 적별 수량 덮어쓰기를 제공한다. 여러 보상을 등록하며 항목별 독립 확률 0~100%로 동시에 당첨될 수 있다. 상대 가중치 추첨은 사용하지 않는다.
- 이번 보상 범위는 정의·편집·계산과 기존 배치 재화 지급까지다. 아이템 보관·영구 저장·설계도 등은 추후 확장한다.
- 상태: 1차 구현과 기능 검증 완료. 대표 변형 데이터를 만든 뒤 시험 전투에서 실제 반영을 확인하는 제작 전 과정과 제작 편의·응답성 평가는 별도 확인 대상으로 남긴다. 상세 증거와 범위는 2.14절을 따른다.

특별 전리품은 짧은 자동 소멸 타이머를 두지 않는다. 확보 캐릭터가 죽거나 다른 명령을 받으면 확보만 취소하고 전리품은 유지한다. 각 라운드 휴식과 승리 후 최종 휴식에서 남은 특별 전리품을 회수할 수 있다. 장비 변경 화면과 전리품/연금 선택 화면은 기존 중첩 팝업 정지 계약을 재사용한다.

**0.8.1 추가 확정 — 사용자 답변, 당시 구현 대기. 최신 구현은 2.9절:**

- 휴식은 시간 제한 없이 유지하며 다음 라운드는 버튼으로 직접 시작한다.

- 공방 공격 중인 적은 근접 아군이 실제로 저지할 때만 해당 아군으로 공격 대상을 전환한다. 주변 아군의 접근만으로 전환하지 않으며, 저지 해제 시 공방 공격을 재개한다. 공방 도착 전의 대상 선정과 구분한다.

### 2.12 1920 × 1080 기준 표시 확대 — 2026-09-18

- 사용자 첨부 Tangy TD 화면보다 살짝 작은 비율로 조정했다. 전장 표시 범위는 48 × 27이며 기존 72 × 40.5 대비 월드 요소가 50% 커진다. 중간 단계의 20% 확대 시안은 최종 첨부 기준으로 교체했다.

## 4. 단계별 제작 계획

달력 날짜 대신 통과 조건으로 순서를 잡는다. 확정되지 않은 조건에 의존하는 구현은 대기한다. 경로·지갑·정지 기반의 구현·개별 검증과 전체 전투 단계 통과를 구분한다.

### 5.1 SOLID 적용 체크

- [ ] 단일 책임: 피해 숫자를 표시하는 코드가 처치 보상과 성장 저장까지 처리하지 않는다.
- [ ] 개방·폐쇄: 새 클래스는 공격·특성 정의를 추가하는 것으로 표현하고 공통 계산의 대규모 분기를 피한다.
- [ ] 리스코프 치환: 다른 공격 방식도 대상 유효성·처치 한 번·결과 규칙을 지킨다.
- [ ] 인터페이스 분리: 잔액 조회만 필요한 화면에 저장 초기화·결과 확정 권한을 노출하지 않는다.
- [ ] 의존성 역전: 성장·보상 계산은 특정 전투 장면과 효과 패키지에 직접 의존하지 않는다.
- [ ] SWUtils와 연결할 경계가 명확하며 동일한 공통 기능을 별도로 중복 제작하지 않는다.
- [ ] 선택 후보가 영구 해금되는 상태와 해당 맵에서 효과가 활성화되는 상태를 분리한다.
- [ ] 적의 경로 이동과 캐릭터의 이동 명령·교전 저지를 하나의 거대 관리 객체로 합치지 않는다.

### 5.2 명칭과 주석

- 새 코드의 이름은 의미를 풀어 쓴다. 예: `DefenderDefinition`, `BattleRewardLedger`, `ClassProgression`, `MapDefinition`.
- 직접 만든 Unity 객체·프리팹·데이터 이름은 영어를 사용하고 객체는 PascalCase로 통일한다. 예: `Canvas`, `WorkshopAttackPoint`, `PurchaseWarriorButton`. Tilemap은 `역할_Tilemap` 형식을 사용한다. 화면 문구와 XML 주석은 한글로 작성한다. 외부 에셋의 기존 이름은 일괄 변경하지 않는다.
- 널리 쓰이는 Hp, 공식 제품명, 기존 패키지의 정확한 타입명은 연결을 위해 사용할 수 있다.
- 프로젝트 네임스페이스와 SWUtils 스타일을 기준으로 중괄호·필드·직렬화·속성의 일관성을 맞춘다.
- 프로젝트용 컴포넌트와 데이터는 적합한 경우 `SWMonoBehaviour`, `SWScriptableObject`를 사용한다. 순수 계산 객체에 불필요한 컴포넌트 상속을 강요하지 않는다.
- 공개 계약·비자명한 규칙에는 한글 XML 주석으로 역할, 입력 의미, 반환·실패 조건을 적는다.
- 기존 타입명과 저장 키 변경은 장면·프리팹·저장 참조를 확인한 뒤 별도 이관한다.

### 7.2 직접 제작 편의와 단계별 확장

- **기본 제작 순서:** 종류별 편집기 열기 → 새로 만들기 또는 복제 → 필수 정보 입력 → 외형·효과·보상 등 참조 연결 → 검사 → 시험 스테이지에서 확인. 파일 경로나 코드 수정을 반복해서 요구하지 않는 흐름을 목표로 한다.
- **입력 부담 완화:** 필수·선택 항목과 입력 단위를 구분하고, 확정된 기본값·예시를 제공한다. 템플릿은 이미 유효한 데이터에서 시작하며 미정인 게임 수치·규칙을 기본값이라는 이유로 확정하지 않는다.
- **연결 편의:** 참조 필드에서 대상을 검색·확인하고 관련 데이터를 열거나 만들 수 있게 한다. 스프라이트·프리팹 등 외형은 미리보기로 확인하여 잘못된 연결을 줄인다.
- **반복 제작 편의:** 같은 종류의 변형은 복제 후 차이만 수정하고, 원본과 복제본의 참조 공유 여부를 확인할 수 있게 한다. 공세·제작 재료처럼 반복되는 목록은 추가·삭제·순서 변경을 제공한다.
- **대량 제작 편의:** 편집-007에서 수치 표 비교·선택 항목 일괄 수정·템플릿 기반 변형 제작을 제공한다. 적용 전 대상과 변경값을 확인하고 모든 입력을 검증한 뒤 묶음으로 적용한다. 실행 취소·다시 실행도 묶음 단위로 확인한다.
- **기능별 확장:** 전리품 → 장비 → 성장 → 선택·위협·연금 → 스킬 순으로 해당 기능 개발과 전용 편집을 연결한다. 상세 화면 배치·템플릿 구성·기본값·미리보기 범위는 실제 제작할 대표 데이터와 함께 착수 시 확인한다.

### 7.3 편집기 완료 체크

현재 7종 편집기의 공통 범위와 앞으로 추가할 기능의 전체 완료 조건을 구분한다. 실제 제작 전 과정·저장용 식별자·대량 제작 항목은 아직 최종 완료가 아니다.

- [x] SWUtils 공통 테마·탐색 기능과 프로젝트 전용 검사·편집 세션을 구분하고 기존 참조를 유지해 편집기 7종에 연결했다.
- [ ] 사용자가 지원하는 규칙 안에서 코드 수정 없이 대표 데이터를 새로 만들거나 복제하고, 참조 연결·수정·검사·실제 실행 확인까지 완료했다.
- [ ] 생성 위치·이름·저장용 식별자 규칙을 확인했으며, 이름 변경·복제·취소로 기존 참조나 저장 식별자가 의도치 않게 바뀌지 않는다.
- [ ] 잘못된 입력·누락 참조·중복 식별자는 문제 위치를 표시하고, 실패한 생성·수정으로 원본이나 일부 데이터만 변경되지 않는다.
- [x] 현재 지원 데이터의 적용·저장·실행 취소·다시 실행과 같은 Unity 세션의 창 재열기에서 초안·참조를 확인했다.
- [ ] 미리보기와 실제 게임 결과가 일치하고, 실행 중 변화가 원본 데이터에 저장되지 않는다.
- [ ] 대량 제작 전 표 비교·일괄 수정·템플릿 복제·전체 검사를 확인했으며, 선택하지 않은 데이터는 변경되지 않는다.
- [ ] 직접 제작에 걸린 시간·반복 입력·헷갈린 항목·오류 수정 과정을 기록하고, 실제 데이터 수와 시험 환경에서 검색·편집 응답성을 확인했다.

지원 지역과 장비가 정해지기 전에는 거대한 수치 체계를 결정하지 않는다. 큰 수를 장기간 다루기로 확정하면 범위·정밀도·최대 구매·표시 정책을 함께 설계한다. 무한 반복을 선언하고 일반 부동소수점으로 충분하다고 가정하지 않는다.

## 8. 위험에 맞춘 검증 목록

기능을 그대로 따라 하는 중복 테스트보다 손실·중복·전투 결과 오류를 검증한다. 문서 수정만으로 게임 실행 테스트를 했다고 기록하지 않는다.

### 8.1 자동 검증 우선 대상

- [ ] 잔액 부족·조건 불충족·상한 도달 시 연구 구매가 모든 상태를 보존한다.

- [ ] 위협 강화가 파밍 효율 때문에 사실상 강제되지 않고 서로 다른 위험 옵션을 선택할 이유가 있다.

### 8.3 성능의 검증 범위

시작 시험값은 화면 내 적 150개, 수호대 12개, 동시 공격·상태 효과 80개다. 특정 하드웨어에서 가능한 수치라고 확인한 것은 아니다. 기획상 최대 개체 수를 확정한 뒤 최소 사양 후보 장비에서 측정한다.

60프레임을 목표로 선택한다면 프레임당 약 16.7밀리초를 기준으로 평균뿐 아니라 느린 구간을 기록한다. 목표 프레임·해상도·장비는 결정 전까지 미정으로 둔다. 긴 반복에서 메모리 증가, 풀 누수, 화면 밖 효과, 피해 숫자의 비용을 따로 확인한다. 동시 이동 명령·경로 재계산·교전 전환의 비용도 포함한다.

## 11. 다음 행동

공방 실제 공격과 라운드·최종 휴식은 0.9, 직접 위치 배치·공방 체력바·선택 사거리·목적지 표시는 0.10에서 구현·검증했다. 0.11에서 폴더·공방 프리팹·공통 데이터·Main 초기화와 씬별 풀을 정리했고, 0.12에서 코드 스타일과 1920 × 1080 표시 확대를 반영했다. 공통 화면 검증은 2.13절, 편집기·보상 기반의 최신 검증은 2.14절을 따른다. 0.13에서는 데이터 편집기와 직접 제작 편의 계획을 추가했고, 0.14에서 선행 작업인 사용자 제작 공통 전투 화면 교체를 마쳤다. 아래 작업의 미정 규칙은 착수 전에 확인한다.

1. **완료한 편집기·보상 기반을 다음 기능에 활용한다.** 편집-001의 대표 변형 데이터 제작→시험 전투 실행 전 과정만 추가 확인하고, 이미 확정한 화면·적용 방식·독립 확률을 다시 미정으로 돌리지 않는다. 표 비교·일괄 수정은 편집-007에 남긴다.
2. **다음 개발 착수 전**, 아이템 보관과 최소 영구 저장·저장용 식별자·중복 정산의 범위 및 특별 전리품 확보 시간·재명령 처리·포기/재시작 보존·저장 시점을 확인한다. 확보 완료분의 실패 보존 자체는 확정이며 장비·설계도·제작 세부는 이후 확장한다.
3. 자동 획득과 직접 확보를 분리한 특별 전리품 드롭/확보 최소 시제품과 편집-002의 남은 영구 획득 연결을 함께 구현한다. 최소 영구 저장·중복 정산 방지도 함께 구현해 확보 완료분 실패 보존을 검증하고, 라운드·최종 휴식에 회수를 연결한다.
4. 장비 영구 인벤토리와 캐릭터당 2슬롯의 최소 장착/해제 흐름을 구현하고 편집-003을 연결한다. 등급·제작식·드롭 수치는 데이터 설계 단계에서 정한다.
5. 공통 연구·클래스 성장과 편집-004를 연결해 결과→성장→재출전 흐름을 완성한다. 위협 강화·공방 연금과 한 맵 선택은 발생 시점·후보 수·적용 대상 등을 정한 뒤 편집-005와 함께 파밍 반복을 검증한다.
