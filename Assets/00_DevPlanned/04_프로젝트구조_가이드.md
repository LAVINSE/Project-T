자산 이동은 Unity `AssetDatabase.MoveAsset`으로 진행하여 기존 식별자를 유지했다. 어셈블리는 `ProjectT.Runtime`, `ProjectT.Editor`로 단순화했다. 스크립트 이름을 바꿀 때는 `.cs`와 `.meta`를 함께 옮겨 GUID를 유지한다. MonoBehaviour·ScriptableObject 참조는 GUID로 연결되므로 `MovedFrom`·`FormerlySerializedAs` 같은 호환 코드를 두지 않고, 이름이 바뀐 필드·병합된 컴포넌트의 참조는 Unity 편집기에서 직접 다시 연결한다.

## 데이터 편집기

`Project T > 데이터`에서 클래스·적·스테이지·경로·재화·아이템 창을 연다. 하나의 `DataEditorWindow`가 `DataKind`별로 따로 열리며, 창 내부의 데이터 분류 탭은 없고 SWUtils의 공통 테마·내장 인스펙터 스타일과 유틸리티를 활용한다. 목록은 아이콘·자산명·타입, 오른쪽은 간결한 속성 입력이다. 전체 화면 규칙은 전체 기획서 12.3절을 따른다.

| 구성 | 책임 |
| --- | --- |
| `DataEditorWindow` (Creation·Editing·Rewards 부분 클래스) | 목록·검색·도구 메뉴·입력 구성, 템플릿 생성·복제, 종류별 선택과 초안 분리 |
| `DataEditSession` | 원본과 초안 분리, 외부 변경 감지, 검사 후 적용·저장·실행 취소 |
| `DataCatalog` | 지원 종류·폴더·한글 항목 설명, 검색·사용처, 연결 데이터까지 묶은 검사 |
| `DataPreview` | 편집 데이터 미리보기. 시험 장면 복제 서비스는 사용자 요청으로 제거 |
| `DataEditorWindow.uss` | SWUtils 테마를 활용한 목록·인스펙터 배치 |

검사 규칙은 별도 검사 스크립트가 아니라 각 데이터의 `Validate`에 있다. 모든 데이터는 `ProjectData`를 상속하며 실행 중 사용하는 `IsValid`와 편집기 검사 결과가 같은 규칙을 사용한다.

자산은 종류별 기존 폴더에 저장하며 재화는 `Assets/02_Res/Data/Currency`, 아이템은 `Assets/02_Res/Data/Items`를 사용한다. 시험 장면 복제·열기 기능은 제거했으며 적용·저장 후 실제 스테이지에서 반영을 확인한다. 초안의 `SessionState` 보관은 같은 Unity 세션에 한하며 게임 영구 저장을 대신하지 않는다.

## 보상 정의·계산·지급

- `Runtime/Data/Rewards`: `RewardData`의 공통 이름·아이콘·기본 수량, `CurrencyData`·`ItemData`, 적별 참조·수량 덮어쓰기·확률을 담은 `RewardEntry`. 기본 보상 수량과 보유 잔액은 다른 개념이다.
- `RewardService`: 적 처치 시 계산 결과 중 스테이지의 `DeploymentCurrency`와 같은 자산만 합산해 `BattleWallet`에 한 번에 지급한다. `BattleManager`가 처치마다 호출한다. 실패 시 부분 지급하지 않는다. `LastCalculatedRewards`는 마지막 계산 결과이며 아이템 보유 목록·누적 획득 장부가 아니다.

Stage01Data는 `Currency/BattleCoinData.asset`, SkeletonBasicData는 해당 자산·개별 수량 10·획득 확률 100%를 참조한다. `UnitEnemyData.Rewards` 목록으로 처치 보상을 지정한다. 아이템 보관·영구 저장·저장용 식별자·설계도·장비와 특별 전리품 확보는 후속 모듈이다.

## Main과 공통 관리자

빌드 순서는 Main → Stage01_Grassland이다. 공통 관리자(DataManager·SWPool·SWPopupManager)는 SWUtils의 `SWSingleton`을 사용하며 Main 장면에 프리팹으로 배치한다. Main의 `MainSceneEntry`가 관리자 준비 후 Stage01을 비동기로 연다.

편집기에서는 `PlayModeStartScene`이 `EditorSceneManager.playModeStartScene`을 Main으로 지정한다. 다른 장면을 열고 Play해도 Main이 먼저 실행되고, Play 직전 열려 있던 장면(`SessionState`에 기록)으로 이동한다. 빌드와 같은 초기화 순서라서 Resources 로드나 `DefaultExecutionOrder`가 필요 없다. Play 시에는 저장된 장면을 불러오므로 수정한 장면은 저장한 뒤 Play한다.

관리자 싱글톤은 조립 지점에서만 읽는다. `BattleManager`가 `ColorData`를 배치·적 생성·공방 표시에, `BattleUI`가 `SpriteData`를 하단 조작 화면에 전달한다. 표시 컴포넌트는 `DataManager.Instance`를 직접 참조하지 않는다.

- `DataManager`: 공통 설정 자산의 접근점. 현재 `ColorData`와 `SpriteData`를 연결한다.
- `SWPool`: 씬 전환에도 유지되는 단일 객체 풀.
- `SWPopupManager`: 공통 팝업 관리자.

`DataManager.Instance.ColorData`로 공유 색상을, `DataManager.Instance.SpriteData`로 공통 아이콘을 가져온다. `Assets/02_Res/Data/Common/SpriteData.asset`의 Speed Icon 1·2·3에는 각각 1배·2배·3배 아이콘을 연결한다. 하단 배속 버튼은 텍스트 없이 현재 배속에 맞는 아이콘을 표시한다. 다른 공통 설정이 추가되면 의미 있는 타입의 참조를 DataManager에 추가한다. 모든 스테이지·캐릭터·장비 데이터를 한 관리자에 무조건 모으지 않는다. 해당 기능이 필요한 데이터는 직접 참조한다.

같은 ScriptableObject를 여러 곳에서 참조한다고 데이터 본문이 복제되지는 않는다. DataManager의 목적은 공통 설정의 접근 규칙을 정하는 것이다. `Instantiate`로 복사하거나 모든 자산을 전역에서 계속 보유하는 경우는 별도로 판단한다. [Unity ScriptableObject 설명](https://docs.unity3d.com/6000.1/Documentation/Manual/class-ScriptableObject.html)

## 씬별 풀 목록

프로젝트에서 사용하는 SWUtils 타입명은 `SWPoolCatalog`이다. 각 씬의 `SWPoolRegistry`에 해당 Catalog를 연결한다.

| 씬 | Catalog | 현재 등록 |
| --- | --- | --- |
| Main | MainPoolData | 현재 공통 재사용 대상이 없어 빈 목록 |
| Stage01 | Stage01PoolData | OrcWarriorRedUnit 2개, OrcMageRedUnit 2개, SkeletonBasicUnit 12개, AttackTrace 4개 사전 생성 |

사전 생성 수는 최대 생성 제한이 아니다. 실제 수요에 따라 풀에서 추가 생성한다. Registry는 씬 종료 시 이름·그룹 등록을 해제하고, 같은 씬을 다시 열면 등록한다. 반환된 객체는 SWPool에서 재사용한다. 새로운 스테이지에서 사용하는 목록도 별도 Catalog로 관리하며, 동시에 로드되는 씬끼리는 같은 이름의 등록·해제 충돌을 피한다.

## 공통 전투 화면

`UIs/Canvas`는 장면에 두고 그 아래 `BattleScreen` 객체만 `Assets/04_Prefabs/UserInterface/BattleScreen.prefab`의 인스턴스로 사용한다. 이 객체의 스크립트는 `BattleUI`이다. Canvas와 입력 시스템은 공통 화면 프리팹에 포함하지 않는다. 사용자 제작 다섯 화면은 중첩 프리팹으로 유지한다. 원본 프리팹에서 그림·배치를 편집하면 공통 화면에 반영된다. `BattleUI`는 같은 장면의 `BattleManager` 하나를 찾아 상태를 전달하며, 재화와 전투 상태를 보관하지 않는다.

새 스테이지는 Stage01 장면을 복제해 만든다. `BattleController`에는 `BattleManager`, `BattleTimeController`, `BattleInput`, `AttackTraceSpawner`를 함께 둔다. 화면을 장면 간 영구 객체로 만들지 않는다.

플레이 모드에서 Main이 준비한 `TestManager` 객체를 선택하면 SWUtils 인스펙터 버튼으로 전투 시작·다음 라운드, 결과 확인, 스테이지 재시작을 실행할 수 있다. `testStatus`에는 단계·처치·공방 체력·입력 안내가 표시된다. BattleUI의 기존 테스트 버튼·상태 표시·전용 구독은 제거했다.

**2026-09-22 적용:** TestManager는 `SWSingleton<TestManager>`를 사용하며 Main의 독립 객체로 배치했다. 장면 로드·활성 장면 변경·장면 해제 알림으로 이전 전투 구독을 해제하고 현재 전투를 연결한다. 시험 장면 복제 서비스와 전용 편집 화면은 후속 사용자 요청으로 제거했다. 향후 승인된 수동 테스트는 TestManager에 모으며 실제 기능 규칙은 각 모듈에 둔다. 게임 화면의 전투 조작 버튼은 별도 확인 작업이고, 게임 화면이 생긴 뒤에도 TestManager는 유지한다.

현재 코인은 기존 전투 지갑을 읽는다. 표시 함수는 재화를 지급하거나 차감하지 않으며 미연결 재화와 잔액 없음은 `-`로 표시한다. 인벤토리 아이템·필터와 성장·장비·스킬은 후속 데이터 및 기능 연결 대상이다.

통합 유닛 데이터의 `portrait`에는 화면용 초상화를 지정한다. 비어 있으면 프리팹에 연결된 대기 그림을 사용한다.

## 공방과 체력바

`ArcaneWorkshop`은 사용자가 만든 그림·Animator·세로 `ArcaneHealthBar`를 사용한다. 그림의 바닥은 현재 전장 공방 위치에 맞추고, `WorkshopAttackPoint`를 별도로 두어 적의 공격 위치가 그림 피벗에 따라 바뀌지 않게 한다.

- 실제 피해: `Hit` Trigger. 한 번 재생한 뒤 기본 상태로 돌아온다.
- 선택지 제공: `WorkshopView.SetChoicesAvailable(true)` → `Alert` Bool. 선택 완료·취소에는 false. 체력 감소나 낮은 체력으로 Alert를 켜지 않는다.
- 체력 0: 애니메이션 정지, 공방 색상 어둡게 표시, 빈 체력바 배경 유지.
- 선택지 발생 시점·후보 구성은 후속 선택지 기능에서 결정한다. 현재는 호출 계약만 준비되어 있다.

`HealthBar`가 실제 체력과 ColorData의 종류별 배경·Gradient를 연결하며 체력이 바뀔 때만 갱신한다. 공방은 아래에서 위로, 아군·적은 왼쪽에서 오른쪽으로 채운다. `CommonHealthBar`는 두 유닛 프리팹에 중첩하여 원본 수정이 함께 반영되게 했다. 아군 사망 시 숨겼다가 부활하면 복구하며, 풀 재사용 시 새 체력에 다시 연결한다.

## 갱신 방식과 전역 관리

- 현재 전투의 매 프레임 진행은 `BattleManager.Update`에서 적 생성·교전·유닛 이동·부활을 순서대로 처리한다. 유닛은 자체 `Update` 대신 `Tick`으로 진행한다. 새 기능도 매 프레임 처리가 꼭 필요하면 `Update`를 사용할 수 있으며, 알림으로 해결되는 처리에는 쓰지 않는다.
- 표시·화면은 매 프레임 조회하지 않는다. `Health.Changed`, `UnitBase`의 `Initialized`·`HealthChanged`·`Moved`·`MovingChanged`, `UnitAttack.Started`·`Canceled`, `BattleManager.StateChanged`, `BattleInput.SelectionChanged`·`MessageChanged`, `BattleTimeController.PauseChanged` 알림에 반응한다.
- 마우스 입력은 Input System의 `InputAction` 신호로 처리한다. 공격 궤적 사라짐·새 아군 화살표처럼 짧은 연출만 코루틴을 사용한다. `DepthSorting`은 편집 모드에서 소품을 옮길 때만 다시 계산한다.
- 스크립트 실행 순서(`DefaultExecutionOrder`)는 지정하지 않는다. 자기 초기화는 `Awake`, 다른 객체 참조는 `Start`부터 사용한다.
- 열거형은 `ProjectEnum.cs`, 애니메이터 파라미터 해시·전투 상수·표시 색상은 `ProjectDefine.cs`, 공용 수치 검사·선 그리기·재화 문자열은 `ProjectExtension.cs`에만 둔다. 스크립트마다 같은 상수나 검사 함수를 따로 만들지 않는다.

## 코드 작성과 실패 처리

`05_Scripts` 전체는 SWUtils 형태의 영역 구분과 한글 XML 주석을 사용한다. 조건문·반복문·함수는 여러 줄 중괄호 블록으로 작성하고, 정렬은 해당 폴더의 `.editorconfig`와 [코드 작성 규칙](CODING_STYLE.md)을 따른다.

잘못된 입력은 `SW.Util.SWLog` 경고와 `null`·`false` 반환으로 처리한다. 생성에 실패할 수 있는 일반 객체는 `Create` 함수에서 검증하며, 호출자는 성공 여부를 확인한 뒤 상태를 반영한다. 2026-09-18 기준 Standalone 개발 타겟의 `SW_DEBUG_MODE`를 활성화했다. 코드 정리 전 원본과 검증 결과는 `Logs/Development/2026-09-18/CodeStyleRevision`에 보관한다.

## 검증과 복구 자료

2026-09-22 사용자 요청으로 `Assets/05_Scripts/Tests`, `Tools/Verification`과 일회성 표시 이전 스크립트를 제거했다. 수동 전투 버튼은 TestManager로 이전했고 시험 장면 복제·열기 기능은 추가 요청으로 제거했다. 자동 테스트·검증·마이그레이션 코드를 추가할 때는 먼저 사용자 확인을 받는다. 아래 과거 검증 기록은 이력이며 제거한 도구를 다시 생성하거나 실행하라는 지침이 아니다.

사용자가 확인한 Main 배치·장면 유지·인스펙터 방식으로 TestManager를 구현했다. 이 요청은 삭제한 자동 테스트 폴더 복원·새 일회성 검증 도구·백업 생성을 허용하지 않는다. 기본 검증은 Unity 컴파일과 합의한 수동 기능으로 진행한다.

## 종류별 유닛과 애니메이션

`UnitData`를 공통 부모로 두고 `UnitClassData`, `UnitEnemyData`에 능력치·표시 정보·종류별 프리팹을 통합한다. 기존 Appearance 자산과 별도의 동작별 프레임 배열은 사용하지 않는다. ScriptableObject 스크립트와 자산 이름은 `Data`로 끝난다.

- 캐릭터: `OrcWarriorRedData`, `OrcMageRedData`. 기존 전사·마법사의 능력치를 유지한다.
- 적: `SkeletonBasicData`, `SkeletonRedData`, `SpiderGreenData`, `SpiderPurpleData`. 기본 해골의 능력치·보상을 유지하고 나머지 3종은 사용자가 Unity에서 직접 입력한다. 미설정 적은 생성 검증에서 거절하며 Stage01에는 등록하지 않는다.
- 프리팹: `Units/Character/CharacterUnitBase`, `Units/Enemy/EnemyUnitBase`를 상속한 `<종류>Unit` 변형을 사용한다. 데이터의 `Prefab` 참조로 생성할 종류를 결정한다.
- 캐릭터·적은 각자 Animator Controller와 클립을 가진다. 상태 구성과 전환은 유닛마다 달라도 된다.
- 유닛 동작은 SWUtils `SWCategory` 자산이다(`02_Res/Data/UnitAction/<동작>Action`, 코드명 = 동작 이름). `UnitAnimation`의 동작 목록이 동작 자산과 그 Animator의 상태 이름을 연결한다. Idle·Walk·MeleeAttack·Death는 항상 목록에 있고 필요한 유닛만 동작을 추가한다(현재 OrcMageRed의 RangeAttack). 상태 이름을 적으면 편집기에서 해당 상태의 클립을 자동으로 채우며, 상태를 찾지 못하면 데이터 검사에서 알려 준다.
- 공격할 때 재생할 동작은 데이터의 `attackAction`(SWCategory)으로 고른다. 새 공격 동작은 SWCategory 자산 추가 → 유닛 동작 목록 등록 → 데이터에서 선택으로 끝나며 코드를 고치지 않는다.
- 열거형은 코드가 값마다 다르게 처리하는 값(전투 단계·체력바 종류·편집기 데이터 종류)에만 쓰고, 기획자가 늘려 가는 분류는 SWCategory 자산으로 관리한다.
- Animator와 `UnitAnimation`은 SpriteRenderer와 같은 `CharacterVisual` 객체에 있다. `UnitAnimation`은 유닛 상태 알림을 Animator에 전달하고 공격 클립의 `AttackImpact` 이벤트를 전투에 전달한다. 기본 그림은 SpriteRenderer의 그림을 사용한다.
- 공격 클립에는 사용자가 지정한 시점의 `AttackImpact` 이벤트를 연결한다. 이벤트 없이 시간이 흐르는 것만으로는 피해를 적용하지 않는다. 중복 이벤트·취소·사망·이전 대상의 생명에는 피해를 중복 적용하지 않는다.
- 공격 간격이 원본 클립보다 짧으면 해당 공격을 간격 안에 재생하도록 속도를 올린다. 간격이 길면 원래 속도로 끝내고 다음 공격을 기다린다. 이동·사망은 기본 속도를 사용한다.
- 적 처치 정산과 전투 목록 제거는 즉시 수행하며, 사망 클립을 마친 다음 SWPool로 반환한다.

새 종류를 추가할 때는 ① Animator Controller와 클립 제작(공격 클립에 `AttackImpact` 이벤트), ② 기본 프리팹의 변형에 Animator Controller 지정, ③ `UnitAnimation` 동작 목록에 각 동작의 상태 이름 입력, ④ 데이터의 Prefab·공격 동작·능력치를 연결한다.
