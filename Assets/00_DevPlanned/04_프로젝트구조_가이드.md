## Main과 장면 수명

빌드 진입은 Main → Stage01_Grassland다. MainSceneEntry가 공통 관리자 준비 후 스테이지를 연다. 편집기의 PlayModeStartScene도 Play를 Main에서 시작한 뒤 직전에 열어 둔 장면으로 이동시킨다. Play는 저장된 장면을 사용한다.

| 관리자 | 역할 |
| --- | --- |
| DataManager | 공통 ColorData·SpriteData·소울 정의 등 설정 참조 |
| SoulManager | 장면 전환에도 유지되는 소울 지갑 |
| InventoryManager | ItemCatalogData와 영구 보관소 |
| SWPool | 장면을 넘는 객체 풀 |
| SWPopupManager | 공통 팝업 |
| TestManager | Main의 독립 객체. 현재 전투 연결과 수동 버튼 |

공통 관리자는 SWUtils SWSingleton을 사용한다. Resources.Load로 관리자를 만들거나 DefaultExecutionOrder로 순서를 강제하지 않는다. TestManager는 장면 변경 때 이전 구독을 해제하고 현재 전투를 연결한다.

TestManager에는 전투 시작·다음 라운드, 결과 확인, 재시작과 상태 표시가 있다. 새 지급·강제 승리 기능은 승인 없이 추가하지 않는다. 시험 장면·데이터 자동 복제와 열기는 제거했다.

씬별 SWPoolRegistry는 SWPoolCatalog를 참조한다. MainPoolData는 공통 목록, Stage01PoolData는 전사·마법사·기본 해골·AttackTrace를 등록한다. 사전 생성 수는 최대 생성 제한이 아니다. 장면 종료 시 등록을 해제하며 같은 이름의 중복 등록을 피한다.

## 유닛·애니메이션

UnitData가 공통 능력치·프리팹·표시 정보를, UnitClassData와 UnitEnemyData가 캐릭터·적의 고유 설정을 가진다. 외형 전용 데이터를 따로 복제하지 않는다.

- 프리팹은 Units/Character/CharacterUnitBase, Units/Enemy/EnemyUnitBase의 종류별 변형을 사용한다.
- 종류별 Animator와 클립을 연결한다. UnitAnimation은 SpriteRenderer와 같은 CharacterVisual에 둔다.
- UnitAnimation의 동작 목록은 SWCategory와 Animator 상태 이름을 연결한다. Idle·Walk·MeleeAttack·Death를 기본으로 필요한 동작을 추가한다.
- 데이터의 attackAction이 공격 동작을 선택한다. 코드에 애니메이션 상태 이름을 분산하지 않는다.
- 공격 클립의 AttackImpact 이벤트가 피해 시점이다. 중복 이벤트·취소·사망·이전 대상의 생명에는 재적용하지 않는다.
- 공격 대기시간이 클립보다 짧으면 재생 속도를 높인다. 길면 원래 속도로 끝낸 뒤 다음 공격을 기다린다.
- 처치 보상과 전투 목록 제거는 즉시 처리하고 사망 동작 뒤 풀로 반환한다.
- portrait가 없으면 연결된 프리팹의 대기 그림을 초상화로 사용한다.

새 유닛은 Animator·공격 이벤트 → 기본 프리팹 변형 → 동작 목록 → 데이터의 Prefab·공격 동작·능력치 순서로 연결한다. 미설정 적 3종은 사용자가 값을 작성하기 전 생성 검사에서 거부한다.

## SWStat

원본은 Stats 폴더의 SWStat, 개별 데이터 설정은 SWStatOverride, 실행 상태는 RuntimeStatCollection으로 분리한다.

1. 초기화 때 참조·중복·수치를 확인하고 SWStatOverride.CreateStat으로 소유자별 복제본을 만든다.
2. 초기화에 성공한 뒤 새 실행 상태를 연결한다. 실패하면 기존 상태를 보존한다.
3. GetValue로 현재값을 읽고 TrySetBonus로 출처·효과별 증가량을 설정한다. RemoveBonuses는 해당 출처만 제거한다.
4. 값 변경 알림으로 이동속도·최대 체력·표시를 갱신한다. 최대 체력 증가만으로 자동 회복하지 않는다.
5. 재초기화·정리 때 이전 구독과 복제본을 해제한다. 공방도 같은 수명 원칙을 따른다.

18개 정의의 목록은 [전체 기획서의 능력치](01_전체세부_기획서.md#능력치)를 따른다. 정수·양수 규칙은 데이터 Validate에서 확인한다. 배치 전 비용은 클래스 설정값으로 읽는다.

추가 7개 능력치는 저장·조회·표시 기반만 있으며 전투 공식은 없다. RuntimeStatCollection의 증가량 API가 존재해도 장비 장착 서비스가 자동으로 연결되는 것은 아니다.

## 보상 계산과 지급

RewardData는 공통 이름·아이콘·기본 수량이며 CurrencyData·ItemData가 이를 사용한다. UnitEnemyData의 RewardEntry는 정의 참조·수량 재정의·독립 확률·장비 등급 무작위를 설정한다.

처리 순서는 다음과 같다.

1. 전체 요청의 데이터·수량·확률과 등급별 등록 아이템을 확인한다.
2. 항목별 획득 확률을 독립 판정한다.
3. 무작위 등급 장비는 개수마다 가중치 추첨 후 같은 ItemData 결과끼리 합산한다.
4. EnemyUnit.RewardIdentifier별 계산 결과를 보관한다.
5. 소울 저장 → 아이템 저장 → 전투 코인을 반영한다.

EquipmentDropResolver는 양수 가중치 등급마다 정확히 하나의 유효한 등록 아이템을 요구한다. RewardService는 요청당 장비 추첨을 ProjectDefine.Inventory.MaximumEquipmentRollCount(10,000회) 이내로 제한한다. 인벤토리 보유량 제한과는 무관하다.

같은 식별자의 재시도에는 확률·등급을 다시 뽑지 않는다. 일부 영구 파일 저장 후 실패하면 성공분은 유지하고 지급 기록으로 중복을 막는다. 앱 복귀·다음 라운드·승패 확정 때 보류분을 재시도하며 안내를 표시한다. 보류 요청은 전투 메모리에만 있어 종료 후 복구하지 않는다.

LastCalculatedRewards는 마지막 처치의 지급 성공 결과다. 전투 전체의 획득 장부나 클리어 추가 보상으로 사용하지 않는다.

SWSaveDataManager의 로컬 파일 기능을 사용한다. 변경 후보를 저장한 뒤 메모리와 Changed 알림을 반영한다. 지급 없는 빈 저장 파일·자동 백업·클라우드는 만들지 않는다. 손상·미지원 저장은 빈 상태로 덮어쓰지 않는다.

ItemCatalogData는 ItemData 자산의 GUID와 참조를 연결한다. InventoryStack은 저장 수량을 표시 정보에 연결하고, 정의가 없으면 수량을 유지하며 정의 없음으로 표시한다. 파괴 후에도 과거 지급 식별자를 남긴다.

ItemCatalogSynchronizer는 아이템 생성·복제·이동·삭제와 Play 진입 전에 실행용 목록을 동기화한다. 플레이어 저장 수량을 바꾸는 이전 도구가 아니다.

특별 전리품의 양수 수량을 새로 저장하면 InventoryStore.SpecialLootAcquired를 요청당 한 번 알린다. 저장 복원·파괴·중복 요청에는 알리지 않는다.

Inventory UI.prefab은 전체 화면 입력 영역과 Background_Img 패널을 구분한다. ItemScroll/Viewport/ItemGrid에 6열 배치를 두고 MinimumVisibleSlots = 36을 최소 표시 수로 사용한다. 초과 슬롯은 필요에 따라 추가·재사용한다.

아이템 분류 SWCategory는 Common/ItemCategories의 ItemEquipment·ItemBlueprint·ItemMaterial·ItemConsumable·ItemOther다. 재료에 제작 재료·장비 파편을 포함한다. 분류 자산이 사용 효과를 구현하지는 않는다.

파괴 확인창은 1개부터 보유량까지 수량을 받아 InventoryStore.TryDiscard를 호출한다. 저장 실패 시 보유량을 유지한다. 제목 이동은 패널만 옮기므로 전체 화면 입력 영역과 바깥 놓기 판정을 유지한다.

InventoryAcquisitionEffectUI는 기존 아이콘 크기를 기준으로 확대·복귀한다. 정지 중에도 연출이 가능하며 비활성·제거 때 크기와 구독을 정리한다. 획득 연출에서 지급·저장을 다시 호출하지 않는다.

결과 팝업은 UI/Popup/BattleResultPopup.prefab을 사용한다. 사용자 파일명 ChracterDPS UI.prefab은 누적 피해 목록 행이다. 이름과 달리 목록은 누적 피해를, 상세의 공격 카드는 스탯 기반 초당 피해를 표시한다.

## 데이터 편집기

Project T > 데이터에서 클래스·적·스테이지·경로·재화의 독립 창과 ‘아이템·장비 편집기’를 연다. 통합 창은 아이템·장비·장비 효과·장비 등급·스탯 탭을 제공한다. 외형 독립 편집기는 유닛 데이터로 통합했다.

| 구성 | 책임 |
| --- | --- |
| DataEditorWindow | 창·목록·검색·종류 전환·도구 |
| Creation 부분 클래스 | 템플릿/빈 데이터 생성·복제 |
| Editing·Rewards 부분 클래스 | 일반 입력·선택적 검사·보상 설정 |
| Equipment 부분 클래스 | 폴더 제한 분류·등급 효과 선택·스탯 표 |
| Management 부분 클래스 | Ping·파일 이름 변경·표시 정보·삭제 |
| DataEditSession | 원본/초안 분리·외부 변경 감지·저장·실행 취소 |
| DataCatalog | 지원 타입·폴더·한글 설명·검색·사용처·검사 연결 |
| DataPreview | 현재 편집값 미리보기 |
| DataEditorWindow.uss | SWUtils 테마와 입력·스탯 표 배치 |

프로젝트 데이터는 ProjectData 계열을, 스탯·분류는 SWStat·SWCategory를 직접 편집한다. 모두 ProjectData를 상속하는 구조는 아니다.

**저장은 데이터 유효성 검사와 분리한다.** DataEditSession.TrySave는 빈 값·미완성 데이터도 저장한다. 생성·복제도 유효한 데이터만 허용하지 않으며 템플릿이 없으면 빈 양식으로 만든다. 파일 이름·경로·잠금·원본 외부 변경 같은 저장 조건은 확인한다.

‘검사하기’는 현재 초안을, 전체 저장 데이터 검사는 저장된 자산을 확인한다. 데이터의 Validate와 SWStat·SWCategory 규칙을 사용하며 값을 자동 수정하거나 저장을 제한하지 않는다. 런타임의 IsValid·생성·지급 전 검사는 유지한다.

등급 효과는 EquipmentEffectData 타입의 ObjectField로 받는다. 참조를 먼저 직렬화 초안에 반영하고 등급 스탯 영역만 갱신한다. ‘사용 | 스탯 | 기본값 | 값 변경 | 최종’ 표의 입력도 해당 행을 갱신한다. 이 구조는 객체 선택 중 전체 입력이 다시 만들어지는 문제를 줄이기 위한 수정이다.

입력 옆 ‘…’ 메뉴와 중첩 생성·관리 버튼은 제거했다. 별도 참조·사용처 화면 및 분류의 Ping·편집은 유지한다. 파일명 변경은 즉시 저장하며 일반 입력은 저장 버튼에서 반영한다. 초안 복원은 같은 Unity 세션의 재열기·재컴파일 범위다.

## 전장 표시와 갱신

Stage01은 MainCamera, BattleController, SWPoolRegistry, Objects, UIs로 나눈다. BattleController에 BattleManager·BattleTimeController·BattleInput·AttackTraceSpawner를 둔다. Objects 아래에 통행 영역·진입점·공방 공격 지점·환경·공방·유닛·TilemapGrid를 배치한다.

카메라·전장 비율은 [전체 기획서](01_전체세부_기획서.md#콘텐츠와-시각-기준)를 따른다. 타일은 바탕·그늘·흙길·자갈·물·긴 풀·울타리 레이어를 사용한다. 환경 소품은 발 위치와 정렬 그룹으로 앞뒤 관계를 처리한다.

HealthBar는 Health.Changed와 ColorData를 읽는다. 공방은 아래에서 위로, 아군·적은 왼쪽에서 오른쪽으로 채운다. 아군 사망 때 숨기고 부활·풀 재사용 때 새 체력에 연결한다. WorkshopAttackPoint를 그림 피벗과 분리한다.

BattleManager.Update에서 적 생성·교전·유닛 이동·부활을 진행하고 유닛은 Tick을 사용한다. 입력은 InputAction, 표시 갱신은 상태 변경 알림을 우선한다. 이동·시간처럼 매 프레임 필요한 처리만 갱신 루프에 둔다.

열거형은 ProjectEnum, 상수·해시는 ProjectDefine, 공용 검사·표시는 ProjectExtension에 모은다. 로그·실패 처리·한글 XML 주석·정렬은 CODING_STYLE를 따른다. PackageCache의 SWUtils 배포 코드는 프로젝트 기능을 위해 직접 수정하지 않는다.

## 확인 범위

현재 문서는 소스·설정·자산 구조를 기준으로 작성했다. 최신 장비 참조 선택과 표 조작, 실제 보상·저장·인벤토리 사용은 [개발 체크의 사용자 확인 목록](02_개발체크_기획서.md#사용자-확인-목록)에 남겨 둔다.

기본 개발 확인은 Unity 컴파일과 기존 수동 기능이다. 자동 테스트·일회성 검증·이전 코드·백업을 추가하려면 먼저 사용자 확인을 받는다.
